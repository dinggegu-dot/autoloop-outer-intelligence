# 架构决定与待验证问题

长期决策的适用范围、对交接稿的异议和后续实验见[架构依据与逐项核对](../architecture/architecture-alignment.md)。当实验改变以下决定时，在同一变更中记录对应代码版本和结果。

| 问题 | 依据与决定 | 影响及验证 |
| --- | --- | --- |
| 三个智能角色 | 使用同一调用适配器及三个版本化输入输出契约；事件唤醒 | 避免维护多个常驻模型进程。检查空队列零调用 |
| 是否新增调度器 | V1 的 GoalEngine、GoalRuntime 和 Hub 已有轮次、容量及暂停语义 | 草案需要持久化，批准后接回原 Ticket 调度链 |
| 完整 Codex 或轻量接口 | 本机已有通过 ChatGPT 登录的 Codex；先复用只读结构化调用，隔离工作目录和工具，保留可替换适配器 | 真实质量、延迟和用量分别记录。其他供应商的成本优劣尚未测量 |
| 契约与旧 Mandate | 新需求在草案阶段冻结来源，批准时绑定目标、验收、预算和权限；旧单按原协议读取 | 重复批准应幂等；旧卡、越界提案与暂停后的迟到结果应失效 |
| 验收目录 | 按可实际运行的可信能力登记，保存环境、版本和产物指纹 | 人工项保留未验状态，同时验坏样品拒收 |
| GitHub 粒度 | 一个私有开发库、分支、可复验的工程记录和需求矩阵。业务消息留在本机 | 三项工程 Issue 对应治理、接单和验收；不把真实用户数据随 PR 上传 |

团队工单采用 Router 分派、每单订阅、单内验收。原始接单记录与候选用料回执分开，已封稿的内容变更通过新版验证。[当前决定及操作验收](../product/router-ticket-teams.md)
