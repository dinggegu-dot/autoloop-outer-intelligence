# 原工单的方案选择与连续修改

2026-11-26 在本机用正式形态的工作台、独立账本和虚构读书会做了版本升级对照。旧程序基线为 `9298266`，新程序使用原来的签名网关、Codex 运行环境和工单入口。

## 旧单能否继续

- 旧程序把「最好有个合法直接下载的版本」变成验收缺口，导读与海报一起停住。换成新程序，从同一张单发起重新研判。真实模型保留了原需求，工单进入等待批准，期间没有要求测试操作员解释如何验收。
- 在旧程序签收一份带有「白桦」识别词的手册。升级后，从该签收件继续两轮。第二轮增加集合地点「南门」，第三轮增加「无障碍入口」。三轮使用相同的工单号。每轮经真实模型制作、复验和试验操作员签收，第三版同时包含三项内容。
- 每次开新轮时重复发送同一个请求，取回同一个事件编号。第二、三轮进行时以及结束后，按原交付编号下载历史文件并核对字节。三版 SHA-256 前十二位依次为 `be57ed24cda1`、`897552af1b6b`、`a6ea19f9d393`。

## 团队会提出怎样的问题

另一张合成单要给两类读者做展览导览，起初没有提供作品名称。团队只询问要读哪部作品。补上虚构短篇及内容后，试验还发现「场地有限」被误当成要系统强制执行的权限。修正条件分类后，在同一单重新研判并批准，Sol 负责人和 Astra 只读顾问分别提案。工单实际进入等待选择，给出「首读入门」与「熟读深谈」，推荐首读入门。

## 界面与故障回归

正式 Google Chrome 在 1440 和 390 像素宽度下，实际操作了只填目标建单、选择团队推荐、从旧缺口重新研判、填写续改、取消确认后继续填写，以及历史文件下载。这组浏览器试验接入合成回执。两个宽度均无横向溢出或页面脚本错误。

隔离服务测试另覆盖中文文件名和空格、同单重复和并发提交、相邻工单误投、损坏的旧归档，以及本轮再批准后重建工作区。只将上轮签收件带入新授权。独立复核用相反案例检查了漏掉第二份交付物、把增加附录误当作删除旧要求、把场地有限误当权限、把实时可订误当成可由文档证明等问题。

从线上程序副本演练程序回退，九项程序文件或目录均与升级前一致，测试账本中新增加的工单记录仍可读取。
