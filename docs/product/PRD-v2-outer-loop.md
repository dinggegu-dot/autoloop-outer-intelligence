# Autoloop V2.0 — Intelligent Outer Loop & GitHub-Native Development

**项目性质：已有 Autoloop 系统的完整升级**

**开发执行方：Codex**

**开发目标：建立基于 DeepSeek Super-agent 思想的智能外层任务治理系统，同时将整个项目转为 GitHub 版本化、可追溯、可恢复的规范开发体系。**

---

# Part 1. 项目背景与最高目标

## 1.1 项目现状

当前 Autoloop 已经具备以下能力，具体实现及证据需要重新审计：

- SQLite 持久化 Ticket、Mandate、Plan、Assignment、Run 和检查点。
- 飞书机器人与网页看板双端交互。
- 程序化任务队列与容量控制。
- 真实 Codex 执行。
- 多个独立 Codex Run 并行执行。
- 工作包级局部返工。
- 协调器重启恢复。
- 执行结果回执丢失后的恢复。
- 用户通过飞书暂停、网页续办。
- 基于预设验收条件的软件任务交付。

上述能力已在此前报告中提供部分本地验证结果，但不能仅凭报告认定它们均已达到生产级水平。

本轮开发必须检查实际源码、数据库结构、运行配置、既有测试和验收证据。

## 1.2 主要问题

目前系统已经能够在明确目标、执行步骤和检查标准的情况下自动工作。

但是面对陌生、模糊、复杂的用户需求，仍然存在以下核心缺口：

**问题一：智能接单不足。**

用户在飞书提出一句自然语言需求后，系统尚不能稳定完成目标理解、任务归属、关键歧义判断、最小必要追问和正式需求确认。

**问题二：验收能力不通用。**

当前验收以部分本地 Python 工具、预设输入输出与固定测试为主。

对于 Web 软件、桌面应用、音频软件、数据分析、报告或其他陌生交付物，尚缺少稳定的验收方式发现、选择、执行和证据管理机制。

**问题三：跨阶段目标协调尚不完整。**

当 Codex 已经完成若干工作包，但整体目标仍未实现时，系统需要能够根据原始目标、执行结果和验收证据，自主判断继续、修复、重新规划或请求用户决策。

**问题四：开发记录和代码管理需要统一。**

现在必须将整个 Autoloop 项目的源代码、PRD、架构决策、开发计划、测试及变更记录规范化管理，并与 GitHub 保持同步。

目标是任何一次修改，都能够回答：

- 为什么修改？
- 修改了哪些代码？
- 对应哪项需求？
- 经过了什么测试？
- 是否影响原有功能？
- 哪个版本可以恢复？
- 当前还有哪些未完成事项？

## 1.3 最终产品目标

用户只需要提出一次目标，并批准必要的执行边界。

Autoloop 应能够自动完成：

**理解目标 → 澄清必要问题 → 设计验收 → 正式授权 → Codex 执行 → 验证结果 → 继续或重规划 → 最终交付。**

用户不应该因为普通技术选型、开发阶段结束或正常测试失败而被频繁要求回复“继续”。

只有重要产品决策、授权变化、不可逆操作、预算超限或无法自动验证的关键结果，才应要求用户参与。

# Part 2. 本次开发的明确边界

## 2.1 保留现有 Autoloop

不得以重新设计为理由，直接替换已经验证有效的：

- SQLite 正式任务状态管理；
- 现有调度器；
- Codex Executor；
- 多 Run 并行机制；
- 飞书与看板；
- 任务暂停、取消、续办；
- 已有恢复和验收机制。

应优先通过增量修改扩展它们。

如果发现确实必须重构，先提供证据、迁移方案、回滚措施和影响范围。

## 2.2 不引入 DSH

本项目是独立的 Codex Autoloop 项目。

不安装、不集成、不迁移到 DSH。

未来 DSH Super-agent 将作为另一个独立项目研究和开发。

## 2.3 不重新开发 Codex 已有能力

不要重建 Codex 的模型推理循环、代码编辑、工具调用和原生子 Agent 通信机制。

Outer Loop 只负责目标治理，Inner Loop 保留已有执行能力。

## 2.4 GitHub 是开发过程的权威来源

GitHub Git 仓库保存代码和版本化工程文档。

但用户工单、飞书消息、授权、运行状态等仍以现有 Autoloop 运行数据库为权威来源。

不得将整个运行数据库复制到 GitHub，或使用 GitHub Issues 替代现有业务 Ticket 数据库。

# Part 3. PRD — 产品需求文档

## 3.1 目标用户与场景

目标用户希望通过飞书或网页，向 Autoloop 提交复杂工作目标。

系统需要承担原本由用户不断执行的任务协调工作，包括：

- 理解需求；
- 明确交付边界；
- 选择验收方法；
- 调度执行；
- 处理阶段结果；
- 组织必要返工；
- 向用户提供真实交付证据。

本轮优先针对软件开发类目标形成完整闭环，但领域模型应允许后续扩展至其他交付物类型。

## 3.2 核心用户旅程

**场景一：陌生需求接单**

用户通过飞书发送：

“帮我做一个文件名索引工具。我想按前缀查文件，新增或删除文件后也能更新索引。”

系统应：

1. 保存原始请求。
2. 检查用户身份和消息来源。
3. 判断是否属于已有 Ticket。
4. 对新目标创建稳定的草案工单。
5. 使用 LLM 形成初步目标草案。
6. 判断是否存在真正影响交付的关键歧义。
7. 必要时提出一个具体问题。
8. 形成正式目标与验收草案。
9. 向用户提交一次性确认卡。
10. 经过有效授权后，才开始执行。

**场景二：同一工单的后续沟通**

用户回复原飞书卡片：

“先把前缀查找做出来，再做增量更新。”

系统应将其关联到原工单，识别是优先级调整还是需要变更目标，并检查是否涉及授权变化。

同一工单的普通反馈不应重复建立新的 Ticket。

**场景三：复杂软件验收**

Codex 已提交文件名索引工具的候选交付版本。

系统根据已确认的验收条件实际运行查询和增量更新，检查旧文件、新增文件和已删除文件的查询结果。

如果脚本无法运行，或查询和更新未达到任一必需条件，必须拒绝通过。

若工单约定由用户签收，系统在客观检查通过后等待用户对该交付版本作出决定。

**场景四：最终目标未达标**

Codex 已完成全部计划工作包，但整体验收失败。

系统应识别失败证据，判断是普通修复、技术重规划还是需要用户决定，并在授权范围内继续。

## 3.3 功能需求

### FR-01：统一事件接入

飞书和网页事件进入统一 Event Gateway。

必须支持：

- 消息来源和发送者身份；
- 原始事件 ID；
- Thread / Card 关联；
- 事件去重；
- 事件持久化；
- 处理状态；
- 审计记录。

明确回复关系优先于 LLM 的语义相似性推测。

### FR-02：智能任务归属

使用 DeepSeek Super-agent 的 Eval 思想。

先执行确定性的 Policy Gate，再使用 LLM Assessment 处理复杂语义。

必须区分：

- 新目标；
- 已有工单补充；
- 澄清回答；
- 修改请求；
- 状态查询；
- 暂停、恢复和停止；
- 其他消息。

不能仅根据主题相似度自动合并任务。

如果多个工单都可能匹配，应请求用户选择或提供更多依据。

### FR-03：Goal Draft

为新任务生成版本化目标草案。

至少记录：

- 目标摘要；
- 交付物；
- 明确必要功能；
- 限制与禁止事项；
- 重要非功能需求；
- 模型提出的默认假设；
- 尚未解决的关键问题；
- 初步验收要求；
- 每项信息的来源。

必须区分用户明确要求与模型建议。

### FR-04：最小必要澄清

Intake Assessor 必须判断不确定性是否真正影响：

- 交付物形式；
- 核心功能；
- 验收标准；
- 执行权限；
- 重大成本；
- 不可逆操作。

对于可以安全默认、可逆且低影响的细节，应记录假设并自动继续。

对于真正关键的问题，一次提出一个具体问题，并尽量提供清晰选项。

不能靠自动批准绕过用户必须作出的决定。

### FR-05：Goal Contract

建立版本化的目标契约，明确用户批准的交付目标与范围。

目标契约应关联：

- Ticket ID；
- Goal Revision；
- 交付物；
- 核心必要功能；
- 明确约束；
- 假设及其处理方式；
- 用户批准事件；
- 原始需求引用。

在正式授权之前，可以存在草案 Ticket，但不得启动超出澄清和允许的只读分析范围的工作。

这属于本系统对 DeepSeek Ticket / Mandate 模型的明确扩展。

### FR-06：Acceptance Contract

在正式开发前，为目标生成版本化验收契约。

每项验收条件至少记录：

- Criterion ID；
- 对应 Requirement ID；
- 验收目标；
- 必需或可选；
- 验证类型；
- 验证器编号及版本；
- 通过条件；
- 所需测试输入；
- 所需证据；
- 来源与批准记录；
- 无法自动验证时的处理方式。

正式验收标准不得由执行 Agent 单方面降低。

### FR-07：Mandate 与授权版本

将正式批准的目标、验收标准、执行权限及预算绑定到有效 Mandate。

用户批准必须绑定具体契约版本。

旧审批卡不能批准新版契约。

扩大权限或重大范围变更，需要新的正式授权记录。

过去的授权记录不可覆写。

### FR-08：Intelligence Service

新增统一智能决策服务。

包含三个逻辑角色：

**Intake Assessor**

负责理解消息、目标归属、草案形成和必要澄清。

默认采用单次 Structured LLM Call；需要额外检索事实时，才升级为受限 Agent。

**Acceptance Designer**

负责将用户目标转换为可验证的验收方案。

允许查询系统验收器目录、目标契约和验证环境。

不得修改正式授权或直接宣布验收通过。

**Goal Coordinator**

负责整体目标未达标、反复失败、跨阶段重新规划等复杂情况。

读取持久目标、计划、预算与证据，提出下一步行动建议。

不得直接执行代码、扩大 Mandate 或单方面宣布最终完成。

三个角色不要求分别运行三个常驻进程。

### FR-09：可信验收器目录

建立 Acceptance Registry。

支持扩展不同交付类型的验证方法。

初期至少考虑：

- Python / CLI；
- Web 应用；
- 文件及数据交付；
- 实际进程启动；
- 功能输入输出；
- 独立模型审查；
- 用户人工验收。

后续可扩展音频、桌面应用和其他领域验证器。

验收器必须有明确版本、适用范围、执行方法、结果 Schema 与证据格式。

未知任务可以提出新的验证需求，但不能因为没有验证器就宣称完成。

### FR-10：目标级验收与继续

必须区分：

- Run 完成；
- 工作包完成；
- 阶段完成；
- 最终 Goal 完成。

最终目标验收必须基于当前有效契约和对应交付版本。

当某些必要条件未达标时，系统应返回明确状态：

- Continue；
- Repair；
- Replan；
- Request Approval；
- Blocked；
- Verified Complete。

最终状态转换仍由 Engine 核查后执行。

### FR-11：飞书与网页的一致交互

同一 Ticket 在飞书和网页展示统一状态。

用户应能够看到：

- 当前目标；
- 已批准范围；
- 待确认问题；
- 正在进行的工作；
- 当前验收结果；
- 下一步由谁决定；
- 最终交付物及证据。

所有审批按钮都必须携带 Ticket ID、目标版本和操作身份。

### FR-12：日志、成本和可解释性

保留模型智能判断记录，包括：

- 智能角色；
- 模型与配置版本；
- Prompt 版本；
- 输入快照引用；
- 结构化输出；
- 决策依据；
- 工具调用概要；
- 耗时和用量；
- 最终 Engine 决策。

记录应符合权限与隐私要求。

# Part 4. 技术架构

## 4.1 总体结构

采用：

**Event Gateway → Policy Gate → Intelligence Service → Autoloop Engine → Existing Codex Execution → Evaluation → Goal Decision**

其中 Intake、Acceptance 和 Goal Coordination 均属于外层智能决策。

Inner Loop 的现有实际执行与恢复机制原则上不变。

## 4.2 Intelligence Service 内部设计

实现四个共享基础组件。

**Context Builder**

根据任务类型读取最小必要的正式上下文。

不将全部历史聊天直接复制到 Prompt。

每个模型调用必须绑定有效输入快照和版本。

**Model Adapter**

封装模型调用。

支持：

- 结构化输出；
- 模型与思考强度配置；
- 超时和有限重试；
- 用量记录；
- 失败分类；
- 后续替换模型。

代码仍由 Codex 开发；运行时外层 LLM 可通过现有 Codex 接口或经验证的其他模型接口调用。

**Tool Gateway**

控制受限 Agent 的工具访问。

初期只提供必要的只读工具，例如：

- `list_candidate_tickets`
- `read_thread_context`
- `get_ticket_snapshot`
- `read_goal_contract`
- `list_available_verifiers`
- `inspect_verification_environment`
- `get_execution_summary`
- `get_evidence`

不得向外层智能 Agent 开放不受控的数据库写入、任意 Shell 执行、授权批准或全局插件配置修改。

**Decision Validator**

对所有模型建议进行：

- Schema 校验；
- Ticket 和 Evidence 引用真实性检查；
- 预期版本校验；
- 权限检查；
- 允许操作类型检查；
- 当前状态合法性检查；
- 幂等检查。

模型建议只是一种 Proposal，不是正式决定。

## 4.3 结构化输出契约

为三个智能角色分别定义版本化 JSON Schema。

### IntakeDecision V1

至少包含：

- `schema_version`
- `event_id`
- `intent`
- `candidate_ticket_ids`
- `relation_evidence`
- `goal_draft`
- `assumptions`
- `critical_ambiguities`
- `proposed_question`
- `suggested_action`
- `input_snapshot_revision`

### AcceptanceProposal V1

至少包含：

- `schema_version`
- `ticket_id`
- `goal_revision`
- `artifact_types`
- `requirements`
- `criteria`
- `verifier_candidates`
- `verification_gaps`
- `human_review_requirements`
- `source_refs`

### GoalCoordinationProposal V1

至少包含：

- `schema_version`
- `ticket_id`
- `goal_revision`
- `acceptance_revision`
- `plan_revision`
- `decision`
- `reason`
- `evidence_refs`
- `proposed_changes`
- `requires_scope_change`
- `requires_human_approval`

具体字段名称应与现有项目风格对齐，但语义与版本关系不得缺失。

## 4.4 持久化与并发原则

必须保证：

- 同一外部事件不会重复创建正式任务。
- 同一用户操作不会重复批准。
- 过期 LLM 建议不会覆盖新版目标。
- 用户暂停和停止优先于自动继续。
- 未经批准的范围变化不能继续执行。
- 旧版本验收证据不能证明新版交付成功。
- 模型调用失败不导致事件无声丢失。
- 运行进程重启后可恢复待处理的智能判断和正式业务操作。

优先复用现有 SQLite 事务、队列和恢复机制。

对外部通知采用持久化待发送记录与异步投递，避免状态提交成功但消息发送失败造成不可追踪差异。

## 4.5 验收安全

验收器不得直接信任执行 Agent 的自然语言汇报。

必须根据真实产物、代码版本和受控测试环境产生证据。

新增验证器的有效性需要检查，执行 Agent 不能随意修改受保护的验收预期。

测试结果必须关联：

- Artifact ID；
- Git Commit 或不可变产物版本；
- SHA-256 摘要；
- 验收契约版本；
- Verifier ID 与版本；
- 运行环境；
- 结果及证据引用。

用户主观验收必须明确标记，不能伪装成自动验证。

# Part 5. GitHub-Native 开发体系

这是本次任务的另一项核心交付，必须与功能开发同步完成。

## 5.1 先审计，再操作 Git

开始时检查：

- 当前 Git 仓库；
- 分支与 HEAD；
- 工作区未提交修改；
- 暂存区；
- 未跟踪文件；
- ignored 文件；
- 已配置的 GitHub Remote；
- 是否已存在 GitHub Repository；
- 是否存在真实运行中的 Autoloop 任务；
- 当前数据库及工作目录。

绝对不要直接执行 `git reset --hard`、`git clean -fd` 或其他会破坏现有状态的命令。

先建立仓库外完整恢复基线，并通过一致性方式备份 SQLite 数据库及 WAL 状态。

恢复基线要能够还原现有代码、配置、测试资产及需要保留的未提交工作。

## 5.2 建立 GitHub 私有仓库

优先检查当前项目是否已有正确的 GitHub Remote。

如果已有，复用它，不重复创建仓库。

如果没有，在具备相应权限的情况下创建新的 **Private Repository（私有仓库）**，并将现有项目安全接入。

禁止自动将仓库设为 Public。

禁止未经检查直接上传整个本地工作目录。

首次 Push 前必须检查：

- `.env` 和 API Key；
- Token 与登录凭据；
- SQLite 运行数据库；
- 飞书用户数据；
- 私人文件；
- 本地缓存；
- 不适合公开或共享的日志；
- 生成的大型二进制文件；
- 第三方版权资产；

# Part 7. 安全、权限和开发约束

以下要求优先级高于自动完成速度。

1. 不破坏已有 Autoloop 数据和工作状态。
2. 不直接清理未提交代码。
3. 不自动公开 GitHub 仓库。
4. 不上传 Token、密钥、私人文件和原始运行数据库。
5. 不在未经授权的情况下产生付费、外部发布或不可逆操作。
6. 不将 LLM 建议当作用户正式批准。
7. 不允许外层 Agent 直接绕过 Engine 修改任务状态。
8. 不让执行 Agent 自行降低用户批准的验收条件。
9. 不把模拟运行结果描述为真实模型执行成功。
10. 不将 DSH 项目合并进本仓库。
11. 不为了符合新架构而重写已验证有效的模块。
12. 不在每个普通开发阶段反复要求用户确认。
13. 不因一次 Codex Run 结束就宣布最终目标达成。
14. 不通过无限重试或无限模型调用掩盖失败。
15. 不自动合并未经审查的高风险 PR。

涉及大规模重构、敏感数据、重大权限变化或不可逆操作时，必须先提供影响分析并获取必要批准。

# Part 8. 质疑与澄清

本项目要求 Codex 主动对架构设计进行审查，而不是机械执行。

至少审查以下问题：

**Q1：是否真的需要三个智能角色？**

如果能够通过一个共享的模型调用基础和三个不同的任务契约实现，就不得无理由创建三个长期运行的 Agent 进程。

**Q2：现有 Autoloop 是否已经实现某些目标能力？**

必须先验证再开发，禁止重复建设。

**Q3：Codex 是否适合运行所有外层判断？**

应比较完整编程 Agent 与轻量结构化 LLM 调用的成本、延迟及效果。

**Q4：新目标契约是否与旧 Mandate 模型冲突？**

必须处理草案工单、授权版本、执行中的范围变更和恢复规则。

**Q5：验收器设计是否过度复杂？**

优先用真实业务场景证明必要性，既不做只能通过固定测试的封闭系统，也不引入缺乏业务价值的复杂框架。

**Q6：GitHub 是否会增加不必要的管理成本？**

GitHub 应主要记录代码、正式开发决策和可复现证据，不应镜像每条业务运行事件。

所有异议应记录为具体的事实、影响、替代方案和推荐决定。

在不改变用户核心目标的前提下，可以采用有充分理由的更简洁实现。

# Part 9. 最终完成定义（Definition of Done）

Autoloop V2.0 只有满足以下条件，才能宣布本轮升级完成。

### 产品

- 用户可以通过飞书一句话提出陌生需求。
- 系统能够可靠归属任务。
- 系统能够自动形成目标与验收草案。
- 仅对真正关键的歧义进行澄清。
- 用户能够在同一工单中确认范围与验收条件。
- 正式授权之后，Autoloop 能够持续调度 Codex。
- 实际交付物接受与类型匹配的验收。
- 总体目标未达标时，不会错误宣布完成。
- 系统能够继续、修复、重规划或请求用户决策。
- 暂停、停止、重启和恢复保持可靠。

### 工程

- 新代码通过适用的自动化检查。
- 原有关键能力没有未披露的回归。
- 新功能有真实测试证据。
- 新增数据和状态变更有迁移及回滚方案。
- 不存在已知的未授权任务推进路径。
- 不存在已知的敏感凭据上传。
- 有可复现的部署和测试说明。

### GitHub

- 正式代码已经安全推送到正确的私有仓库。
- PRD、架构、计划和进度文件与代码版本一致。
- 主要需求均有对应 Issue、PR 和测试记录。
- CI 状态可核查。
- 变更历史和主要架构决策可追踪。
- 当前版本可从 GitHub 重建，并能在受控条件下恢复必要运行环境。
