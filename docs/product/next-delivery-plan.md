# AFR 与 Autoloop 首版执行计划

2026-11-22 · 首批目标平台为 macOS · [总跟踪单 #7](https://github.com/dinggegu-dot/autoloop-outer-intelligence/issues/7) · [产品范围与验收场景](afr-autoloop-product-prd.md)

**下一个交付物是一份别人也能跑通的 AFR。** 新用户只下载 AFR，指定一个投放目录和一个空 Obsidian 库，放入合成材料，关闭 Obsidian 也能自动收录。重新打开后可以从白板回到原文，在本机搜索。随后再用获准的合成版本验 Codex 研读和追问。Autoloop 的前两个验收点分别是单独交付普通工单、连接 AFR 后从飞书交付研究工单。这三个体验各有自己的版本和回退点。

## 第一张实施单怎么做

1. 在 AFR #10 登记本次切片的仓库、`main` 的实时 SHA、工作分支和合成样本；关联 #8 的首次初始化要求。旧工作区的差异按文件与远端核对，保留独立网页和原型工作。
2. Codex 从干净副本建短分支，先复现借用现有环境的基线，再在新建 Python 3.11 环境按依赖清单重跑。若安装失败，记下阶段、缺项、环境、修复提交和复验结果。模型和飞书不是这张单的依赖。
3. 验收者只拿候选提交、说明和合成夹具，从空投放目录与空库运行。检查成功路径、失败路径、再次运行，以及回到起点后同一合成用例的结果。把差异、测试摘要和回退 SHA 贴到实现 PR，再更新 #7。第一张单通过后交给自动收录工作包。

## 每轮 Git 交接与恢复

| 时点 | 当轮负责人要留下什么 |
| --- | --- |
| 开工 | 真实远端、目标分支、基线完整 SHA、Issue、范围和验收。检查在途 PR 和工作树。跨库变更各开一个可审阅的 PR，互链并说明兼容顺序 |
| 开发和提交 | 一个可逆目的一个提交。逐路径审阅暂存内容，覆盖源码、测试、设计、合成样本与脱敏证据。真实研报、私人 Vault、凭据、完整运行备份和含正文的日志只留本机 |
| 推送和审查 | 到 GitHub 回读远端 SHA 与 PR 的 base/head。记录本地检查、托管 CI、审查、合并各自状态，以及失败原因、修复 SHA 和复验。AFR 基线上无 Actions；Autoloop 只在 `ci/included/**` 触发 macOS 检查。托管检查仅在确认包含额度内运行 |
| 交接和发布 | Issue 给出实现 PR、实际验证与合并 SHA、上个可用版本、未完成项、下一动作和负责人。部署另记安装的版本、数据格式和恢复点。检查未通过时保留未结状态。发布后从下载链接复核附件和校验值 |

**代码回退。** 尚未合并的变更可追加修正提交或关闭 PR。进入共享分支后另建修复分支，对普通提交或 squash 合并用 `git revert <提交>`；只有确认第一父提交为目标分支的真实 merge commit，才用 `git revert -m 1 <合并提交>`。存在后续依赖时先判断依赖顺序，在隔离副本回退并跑同一验收，再走 PR。共享历史保留原记录。

**运行与数据恢复。** 改数据库、监听器或发布器前，登记版本、配置、输入目录、在途工单、受影响的数据与备份编号。SQLite 用一致性备份；备份和密钥本机保管，GitHub 只记恢复方法和脱敏核对结果。先在独立目录恢复并回读，再决定是否切换。切换前暂停写入，对账备份后新增的材料、笔记、工单和签收，保留并回放可重放的增量。已经发送的飞书消息或外部动作由回执对账，需要更正时在同单补发说明。首版涉及数据格式时，旧程序能否读升级后的数据也要实测。

一次失败的记录应能回答五件事：在哪个 SHA、哪一步失败、影响了哪些数据或工单、用哪个提交或恢复点修复、谁在什么环境复验通过。GitHub 上先看到这个答案的人，应当能接手下一步。
