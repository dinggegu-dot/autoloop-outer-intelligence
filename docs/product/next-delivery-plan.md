# AFR 与 Autoloop 首版执行计划

2026-11-22 · 首批目标平台为 macOS · [总跟踪单 #7](https://github.com/dinggegu-dot/autoloop-outer-intelligence/issues/7) · [产品范围与验收场景](afr-autoloop-product-prd.md)

**首个里程碑是让两个产品的 Agent 在实际入口完成任务。** AFR 的研读和校读要从同一份固定原文产出可信的白板；Autoloop 的执行 Agent 要在一次授权内处理出错和中断，并交出可独立核验的成果。两条开发线可并行。通过核心验收后，再联调飞书、验证自动收录和独立安装，最后制作下载包。

## 技术决定

两款产品的 Agent 统一使用已有的 **Codex harness**，由 Codex 负责模型运行、选择和调用已授权工具、管理会话。角色用职责说明、可用工具、输入范围和交付契约定义，按任务启动。项目提供领域工具、持久业务状态、授权、去重、验收与审计。自研通用 harness、通用模型动作循环和本地模型下载均排除在开发范围外。旧离线试点的领域校验和合成用例可复用。可信的单轮结构化外层判断可以继续维持现状。

建议首轮复用已登录的 Codex CLI 及现有领域函数，为需自主取证的角色仅暴露获准版本的工具。可用 Codex 支持的本机 MCP 作为薄接线，工具返回前重新校验授权。工具和模型所在进程分别测试可见范围，避免其他文件入口绕过资料策略。需要续办的执行选择可持久化的会话，保存它与工单的绑定；授权范围缩小或撤销时重新核对历史上下文，必要时在符合当前权限的新上下文中从检查点续办。本机 CLI 帮助有按指定 ID 恢复的入口，产品接通及隔离效果仍需真实轨迹证明。[Codex 非交互执行](https://developers.openai.com/codex/noninteractive/) · [Codex 工具接入](https://developers.openai.com/codex/mcp/)

### 已复现的 AFR 发布缺口

2026-11-22，在全新临时库使用现行 CLI，输入一份合成材料「星桥样本本月的可用率是 40%，全年可用率未知。」外部草稿的 summary 与 argument 写「星桥样本全年可用率为 40%。」，引用范围仍完整。依次执行 scan、evidence、publish、search、read，发布返回成功，错误结论同时写入完整阅读、白板且可回查，固定原文保留正确说法。该次只验证外部草稿发布路径，模型调用数为零。实现时保留该用例，并用独立的正确草稿验证可正常发布。[AFR 功能单 #21](https://github.com/dinggegu-dot/atom-flow-research/issues/21)

## 开发顺序与验收

| 工作包 | 本轮交付与证据 | 回退办法 |
| --- | --- | --- |
| 1A · AFR 研读与校读，立即开发。[AFR #21](https://github.com/dinggegu-dot/atom-flow-research/issues/21) | 用真实 Codex 在空测试库处理获准的合成材料。研读按完整论证产出草稿；独立校读回看同版原文，拦住错时期、错分母或遗漏反例并指出出处。修复后重校再发布。保留人工改动、复核结论和版本，重放同一请求只发表一次，未授权时模型调用为零。 | 停新派发，保留原件、人工笔记和上一份已验成果；候选稿与已发布稿分别追踪。用回退提交在合成库回读此前版本。 |
| 1B · Autoloop 内层连续执行，与 1A 并行。[Autoloop #3](https://github.com/dinggegu-dot/autoloop-outer-intelligence/issues/3) | 从星球工作台给一次授权，交付一个多步 CLI 与索引，执行器自行拆解。注入跨步骤错误、执行中重启；对账在途 Run，拒绝错误产物，自主修复再跑全量终验。记录用户催办次数、权限与剩余预算、真实工具事件、原会话续接或检查点恢复原因。另测耗尽停止、需人工条件等待签收。 | 停新派工、留在途回执，恢复上个 Worker 和已验证检查点，外部动作状态不明时先对账。 |
| 2 · AFR 研究与工单联调，依赖 1A，两端联调另依赖 1B | 七份合成资料分布于可核对的日期窗口。从飞书或工作台发「总结近七天我上传的材料，指出分歧」，Codex 按需列举、换词检索、读定版、比较和引用。原单追问「哪方依据更弱」，核对父轮、双方引文和未决问题。更改当前稿后旧答案可定位；断开、重启、重复投递均能对账。 | 先断开适配器，恢复上个兼容版本组合。父轮、固定引用和历史报告保留。 |

## 第一轮开发交接

AFR 维护者从远端 main 建功能分支，Autoloop 维护者从 V2 候选分支建独立功能分支。在两张工单各提交一个能重现缺口的合成用例、实现提交、经授权的真实 Codex 验收轨迹、失败与恢复结果。模型动作替身单列。独立验收者从实际入口重复操作，检查用户看到的成果与错误分支，再更新总跟踪单。正式研报模型外发保持关闭；已有权限的本机操作者可核对原件、索引和出站计数。真实语义验收使用许可的合成材料。

## 每轮 Git 交接与恢复

| 时点 | 当轮负责人要留下什么 |
| --- | --- |
| 开工 | 真实远端、目标分支、基线完整 SHA、Issue、范围和验收。检查在途 PR 和工作树。跨库变更各开一个可审阅的 PR，互链并说明兼容顺序 |
| 开发和提交 | 一个可逆目的一个提交。逐路径审阅暂存内容，覆盖源码、测试、设计、合成样本与脱敏证据。真实研报、私人 Vault、凭据、完整运行备份和含正文的日志只留本机 |
| 推送和审查 | 到 GitHub 回读远端 SHA 与 PR 的 base/head。记录本地检查、托管 CI、审查、合并各自状态，以及失败原因、修复 SHA 和复验。AFR 基线上无 Actions；Autoloop 只在 `ci/included/**` 触发 macOS 检查。托管检查仅在确认包含额度内运行 |
| 交接和发布 | Issue 给出实现 PR、实际验证与合并 SHA、上个可用版本、未完成项、下一动作和负责人。部署另记安装的版本、数据格式和恢复点。检查未通过时保留未结状态。发布后从下载链接复核附件和校验值 |

**代码回退。** 尚未合并的变更可追加修正提交或关闭 PR。进入共享分支后另建修复分支，对普通提交或 squash 合并用 `git revert <提交>`；只有确认第一父提交为目标分支的真实 merge commit，才用 `git revert -m 1 <合并提交>`。存在后续依赖时先判断依赖顺序，在隔离副本回退并跑同一验收，再走 PR。共享历史保留原记录。

**运行与数据恢复。** 改数据库、监听器或发布器前，登记版本、配置、输入目录、在途工单、受影响的数据与备份编号。SQLite 用一致性备份；备份和密钥本机保管，GitHub 只记恢复方法和脱敏核对结果。先在独立目录恢复并回读，再决定是否切换。切换前暂停写入，对账备份后新增的材料、笔记、工单和签收，保留并回放可重放的增量。已经发送的飞书消息或外部动作由回执对账，需要更正时在同单补发说明。首版涉及数据格式时，旧程序能否读升级后的数据也要实测。

一次失败的记录应能回答五件事：在哪个 SHA、哪一步失败、影响了哪些数据或工单、用哪个提交或恢复点修复、谁在什么环境复验通过。GitHub 上先看到这个答案的人，应当能接手下一步。
