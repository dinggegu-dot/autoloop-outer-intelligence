# 0. 阅读本文件前必须理解的事情

本文件不是要求重新开发一套 Autoloop，也不是要求立即增加新的 Agent。

它用于向后续负责开发的 Codex 完整传递我们围绕 Autoloop 形成的设计理念、架构决策和真实工程目标。

本项目起源于 GitHub 开源项目：

https://github.com/KKKKhazix/agent-autoloop

我们在其基础上进行了大量二次开发，当前开发仓库为：

https://github.com/dinggegu-dot/autoloop-outer-intelligence

当前系统已具备实际运行、真实 Codex 执行、飞书交互、并行、局部返工和故障恢复能力。

**我们的目标不是继续堆叠功能，而是让这个系统真正成为能够持续承担用户目标的 Autonomous Super-agent（自主超级智能体）系统。**

未来所有优化首先应回答：

1. 这个修改解决了用户的什么实际问题？
2. 是否提高了系统围绕目标自主工作的能力？
3. 是否减少了不必要的人工干预？
4. 是否提高了任务执行与最终交付的可靠性？
5. 是否与现有能力重复？
6. 是否增加了不必要的复杂性、成本或风险？

不能仅因为一种多 Agent 架构看起来先进，就将其加入系统。

另外，我们还计划在 DSH 上独立研究与开发另一套 Super-agent。本文件只适用于 Codex Autoloop，两个项目不得未经要求合并。

# 1. 项目的最终目标

## 1.1 我们最初想解决的问题

使用 Codex 开发复杂软件时，用户通常需要不断承担项目经理的工作：

- 解释目标。
- 确认技术方案。
- 告诉 Codex 开始下一阶段。
- 检查上一阶段是否完成。
- 指导它修复问题。
- 重新启动或续接 Session。
- 告诉它何时可以交付。

即使 Codex 已经拥有很强的代码开发能力，人类仍然在承担大量任务协调工作。

因此，我们希望改变这种工作模式。

**从：用户持续管理 Agent 的执行过程。**

**转变为：用户管理最终目标，Agent 系统负责执行过程。**

## 1.2 理想的用户体验

例如用户通过飞书发送：

> 帮我开发一个自动 DJ 软件，用户可以选择音乐，系统能够自动完成类似专业 DJ 的平滑音乐过渡。

系统应该自动完成：

1. 理解用户真正希望得到什么。
2. 判断是否存在影响交付的关键歧义。
3. 形成可理解的产品目标和初步验收标准。
4. 只要求用户确认必要的目标、权限和重大限制。
5. 自动制定开发计划。
6. 调用 Codex 及必要的子 Agent 执行。
7. 检查阶段结果。
8. 未达标时自动修复或重新规划。
9. 当前 Codex 执行结束后，根据任务状态继续下一步。
10. 发生故障后根据已有状态恢复。
11. 最终交付能够实际使用、具有可靠验收证据的成果。

用户不应该反复发送“继续”。

但系统也不应该无条件执行到底。

重大产品决策、权限扩大、付费、不可逆操作，以及无法充分自动验证的主观质量要求，仍然需要用户参与。

## 1.3 成功标准

Autoloop 的成功不以创建了多少个 Agent、多少次模型调用或者多少个任务节点衡量。

最重要的是：

**一个用户目标能否在明确授权范围内，通过尽可能少的人工介入，最终变成真实、可用、经过验证的交付成果。**

# 2. 核心设计思想：Outer Loop + Inner Loop

这是我们在多轮讨论后确定的最高层架构。

整个系统分成两个逻辑循环。

## 2.1 Outer Loop：外层任务治理

回答五个问题：

- 用户到底想做什么？
- 这项任务应该归谁管理？
- 系统被允许做什么？
- 目前是否正在朝目标推进？
- 什么证据能够证明最终目标已经完成？

外层负责：

**Intake → Goal Contract → Authorization → Scheduling → Goal Evaluation → Coordination → Delivery**

## 2.2 Inner Loop：内层复杂任务执行

回答：

- 这个目标应该怎样实现？
- 怎样拆解任务？
- 是否需要多个 Agent？
- 应该使用哪些工具和技术？
- 遇到技术失败如何修复？
- 如何产出代码、文档或其他成果？

内层负责：

**Plan → Execute → Test → Repair → Replan**

## 2.3 两层的责任边界

Outer Loop 不应该干预 Codex 的每一个函数、文件或普通技术决策。

Inner Loop 不应该擅自扩大用户授权、降低最终验收条件，或者自行决定整个用户目标已经完成。

它们通过正式数据交接：

- Ticket；
- Goal Contract；
- Acceptance Contract；
- Mandate；
- Persistent Plan；
- Assignment；
- Execution Report；
- Artifact；
- Evaluation Evidence。

**外层决定目标是否还需要推进，内层决定具体怎样推进。**

这是整个项目最重要的架构原则。

# 3. DeepSeek Super-agent 对我们的核心启发

DeepSeek Super-agent 是本项目长期任务治理的重要设计参考。

官方研究原型：

https://github.com/deepseek-ai/dsh-superagent-prototype

其核心思想不是简单增加更多 Agent，而是将长期任务生命周期与模型 Session 生命周期分离。

我们重点借鉴以下概念：

| 概念 | 解决的问题 | Autoloop 对应机制 |
|---|---|---|
| Source | 外部任务来自哪里 | 飞书、Web、系统事件 |
| Trigger | 发生了什么事件 | 消息、审批、回执、测试结果 |
| Thread | 哪些消息属于同一讨论 | 飞书原卡与工单讨论关系 |
| Eval | 是否接受、归属或处理事件 | Policy Gate + 智能研判 |
| Mandate | Agent 凭什么执行、能做什么 | 版本化授权 |
| Ticket | 长期存在的工作身份 | 持久工单 |
| Subscription | 后续反馈进入哪个任务 | 消息与工单绑定 |
| Assignment | 哪次具体执行承担工作 | 正式派工 |
| Executor | 谁实际完成任务 | Codex Worker |
| Recovery | 出错后怎样继续 | Run 对账、持久状态和恢复 |

必须明确：

**Ticket ≠ Session。**

**Assignment ≠ Ticket。**

**模型建议 ≠ 授权。**

**执行结束 ≠ 任务完成。**

**重试 ≠ 故障恢复。**

特别重要的是，DeepSeek 的原型以同一个 Ticket 对应的 Executor Session、工作目录和持久记录维持工作连续性。

我们的 Autoloop 采用自己的执行中台与 Codex Run，因此不要求机械复制 DeepSeek 的 Session 设计。

我们要学习的是这些机制背后的可靠性原则，而不是复制其所有代码结构。

此外，我们有意扩展了原始设计：允许一张 Ticket 从未授权的需求草案开始，之后经历确认、授权、开发和验收。首次授权及后续授权变更以不可变记录保存。

这一扩展必须保持严格的权限与版本控制。

# 4. 最重要的技术原则：程序与 LLM 各自负责什么？

我们明确否定两种极端：

**错误方案 A：整个 Super-agent 只由程序化 Workflow 组成。**

这种设计可以可靠调度任务，但在陌生目标理解、复杂验收和跨阶段重规划时，容易缺少智能判断。

**错误方案 B：一个常驻 LLM Agent 管理所有事情。**

这种设计会让任务状态、授权、恢复及资源调度过度依赖模型，增加不可预测性。

最终确定的方案是：

**Event-driven Intelligence + Deterministic Engine + Codex Execution。**

即：

### 程序负责

- 事件去重；
- 身份认证；
- 明确工单关联；
- 正式授权检查；
- 状态转换；
- 持久化；
- 任务调度；
- 并发控制；
- 重试与恢复；
- 预算和权限约束；
- 可信验收执行；
- 正式交付状态。

### LLM 负责

- 模糊用户意图理解；
- 陌生目标整理；
- 关键歧义判断；
- 验收方案设计；
- 复杂跨阶段失败分析；
- 必要的重新规划建议。

### Codex 内层负责

- 技术方案；
- 具体开发计划；
- 代码编写；
- 工具使用；
- 原生子 Agent 协作；
- 软件测试与普通技术返工。

系统不需要模型一直在线推理。

长期存在的是任务、状态和调度职责，而不是一个永不结束的模型对话。

# 5. Outer Intelligence：三个智能角色

我们将外层智能理解成三个逻辑角色。

它们不是必须常驻的三个 Bot，也不要求相互持续聊天。

## 5.1 Intake Assessor：智能接单

负责：

- 理解用户的自然语言目标；
- 判断新任务还是已有任务的后续消息；
- 抽取用户明确要求；
- 形成 Goal Draft；
- 判断是否存在关键歧义；
- 提出最少量必要澄清。

核心原则：

**不确定不等于必须追问。**

例如颜色、普通技术选型和可逆的低影响细节，可以由系统采用合理默认值。

但交付平台、核心功能、重大成本和授权范围的歧义，必要时必须询问用户。

模型不能仅凭内容相似度，将消息强制关联到另一张工单。

明确的原卡、消息引用和工单关系优先于语义推测。

## 5.2 Acceptance Designer：智能验收设计

负责：

- 理解目标要求；
- 识别交付物类型；
- 将需求转换成具体验收条件；
- 匹配可信验证器；
- 指出无法自动验证的条件；
- 提出需要人工验收的部分。

我们认为这项能力尤其重要。

**不能先让 Codex 自由开发，最后由它设计一套容易通过的测试，再宣布自己完成。**

应当在正式执行前建立合理的 Acceptance Contract。

执行中可以完善测试覆盖，但不能未经批准降低核心验收标准。

## 5.3 Goal Coordinator：持续目标协调

负责：

- 判断复杂失败是否需要调整总体计划；
- 分析多轮失败证据；
- 判断工作包完成但最终目标未完成的原因；
- 建议 Continue、Repair、Replan、Request Approval 或 Blocked；
- 在现有成果上继续推进，避免无意义重复工作。

它不是另一个负责写代码的 Codex Lead。

普通 Bug 修复由内层优先处理。

只有跨阶段问题、重大技术路线失败或整体验收不足时，才需要外层协调。

## 5.4 三个角色的实际运行形式

根据本机候选版本 `af48958` 的代码核查：

三个角色已经实现为三种独立的结构化模型决策任务。

它们共用 `outer_model.py` 的 Codex CLI 调用适配器。

当前使用的模式大致为：

`codex exec + --ephemeral + --sandbox read-only + --output-schema`

运行模型为 `gpt-6.2-sol`，三个角色分别采用不同的思考强度：

| 角色 | 当前思考强度 | 实际形式 |
|---|---|---|
| Intake Assessor | Low | 临时结构化 Codex 调用 |
| Acceptance Designer | Medium | 临时结构化 Codex 调用 |
| Goal Coordinator | High | 临时结构化 Codex 调用 |

它们没有分别维护常驻 Agent，也没有为每个角色保存可续聊的 Codex Session。

当前外层执行还显式关闭了 Shell、浏览器、多 Agent、MCP 和其他不必要工具。

这说明：**当前系统已经具有三个智能角色，但没有实现三个自主 Tool Calling Agent。**

这是一个合理的工程选择，不应仅为满足“Agent”名称而重建。

未来只有实际测试证明需要主动检索信息时，才应给相关角色增加受限只读工具。

# 6. 外层最重要的产品机制：Goal Contract 与 Acceptance Contract

## 6.1 Goal Contract

保存用户真正批准的目标。

至少包含：

- 最终交付物；
- 核心必要能力；
- 重要非功能要求；
- 允许和禁止的操作；
- 模型假设；
- 用户确认依据；
- 来源引用；
- 版本。

必须明确区分：

`USER_EXPLICIT`

`USER_CONFIRMED`

`CONTEXT_DERIVED`

`MODEL_PROPOSED`

模型提出的假设不能自动升级为用户确认的要求。

## 6.2 Acceptance Contract

保存怎样证明目标完成。

每项验收要求应关联：

- Requirement ID；
- Criterion ID；
- 验收方式；
- 是否为必需项；
- 验证器；
- 预期结果；
- 证据格式；
- 当前验证状态；
- 来源和版本。

验收结果至少区分：

`PASS`

`FAIL`

`INCONCLUSIVE`

`NOT_RUN`

`ERROR`

其中，无法验证不等于通过。

## 6.3 Mandate

用户正式批准时，系统应同时绑定：

- Goal Revision；
- Acceptance Revision；
- 授权范围；
- 预算；
- 工作目录；
- 禁止操作；
- 身份和审批事件。

过期飞书卡片不能批准新版本目标。

模型不能通过修改 Prompt 扩大权限。

暂停、终止和授权变化必须得到程序化执行。

## 6.4 一次确认，而不是持续确认

理想交互是：

系统先形成完整的目标与验收建议，然后向用户展示一张简短确认卡。

用户确认一次后，普通开发细节、技术选型、测试和返工应在授权内自动完成。

除非出现新的真正重大问题，否则不应该每个阶段都要求用户批准。

# 7. Inner Loop：保留已经验证的 Codex 执行体系

现有 Autoloop 已实现：

- 持久化正式工作包；
- Codex 真实执行；
- 多 Run 并行；
- 工作目录隔离；
- 局部返工；
- 运行中断恢复；
- 回执丢失后的对账；
- 容量控制。

这些不应因为 Outer Loop 升级而重建。

我们也不要求所有 Multi-Agent 必须通过 Codex 原生 Subagent 实现。

应该区分两种粒度：

**跨工作包的独立执行：**

由 Autoloop 分配多个独立 Codex Run。

适合独立验收、隔离写入、并行、取消和局部重试。

**单个复杂任务内部的协作：**

可以使用 Codex 原生子 Agent。

是否值得使用，需要根据真实质量、耗时和用量进行对照测试。

多 Agent 的数量不是目标，最终完成质量才是目标。

# 8. 两层之间怎样维持上下文连续性？

这是我们此前讨论的核心问题之一。

我们不希望一个 Session 结束后，后续 Codex 不知道已经完成什么。

也不希望每次都把完整聊天历史重新注入模型。

因此采用：

**Persistent Task State + Structured Execution Handoff + Artifact References。**

每轮执行需要明确：

- Ticket ID；
- 当前正式 Goal；
- Goal / Acceptance / Mandate / Plan Revision；
- Assignment / Run ID；
- 已完成且通过验证的工作；
- 当前需要完成的子目标；
- 现有代码、Git 版本和其他产物；
- 之前失败的原因；
- 当前验收要求；
- 下一步推荐；
- 授权与剩余预算。

Codex 的 Session History 可以辅助继续，但不能作为唯一的工作记忆。

即使未来替换 Codex 版本、使用新的 Session 或重启服务，正式工单仍应能依据数据库和真实产物继续。

**Ticket 保存任务身份，Plan 保存执行方向，Artifact 保存成果，Evidence 保存验证事实。**

LLM 不应成为这些事实的唯一存储位置。

# 9. Goal Evaluation：为什么工作包完成不等于目标完成？

例如自动 DJ 系统：

音乐导入、节拍分析、播放器和过渡算法都分别通过测试。

但真正播放时，用户仍然觉得歌曲过渡生硬。

此时：

各个工作包可能已完成。

但是整体 Goal 仍未完成。

因此系统至少要区分：

1. Run Completion；
2. Work Package Completion；
3. Stage Completion；
4. Goal Completion。

只有当前有效验收契约中的全部必需条件得到有效证据支持，且必要的人工验收已经完成，才能标记最终完成。

当整体目标失败时：

- 普通局部 Bug → Codex Repair；
- 已有下一阶段 → Scheduler Continue；
- 复杂跨阶段问题 → Goal Coordinator；
- 超出授权 → 请求用户批准；
- 缺少验收能力 → 明确标记 Verification Gap。

不得让执行 Agent 自己降低验收标准。

# 10. 当前 V2.0 实现进度与证据边界

以下来自 2026-11-19 的 Autoloop V2 验收报告和随后对 `af48958` 的本机核查。

它们是目前的工程证据，不应自动解释为已经达到生产环境要求。

## 10.1 已经验证的能力

**真实飞书接单与授权**

用户从飞书提出温度换算工具需求。

系统完成智能接单、目标澄清、验收设计及版本化授权。

首轮代码未通过两项精确 JSON 检查，系统自动派发修复，最后复验 2/2 通过并交付。

**真实非 CSV 软件任务**

会议区间工具完成真实模型接单、验收设计、规划和开发。

最终四项检查均通过，每项在两个独立进程中验证。

**跨阶段协调**

真实 Codex Coordinator 在验收失败后选择 `REPAIR`，随后由另一个 Codex Run 负责实际修复，再由独立执行完成复验。

这一验证的初始目标与部分流程采用夹具，因此不能将它等同于完整陌生复杂目标的自主执行成功。

**恢复与控制**

测试涵盖暂停、续办、协调器重启、迟到回执、重复投递和版本冲突。

**回归**

本机完整回归为 242/242，通过了实际 Seatbelt 检查。

**容量**

五单场景累计 50 个 Run，验证了容量 1 和 4 的领取峰值；模型部分使用离线夹具，不能据此推断真实模型吞吐和成本。

## 10.2 智能能力仍有不足

真实路由样本中，4/5 符合预期。

其中存在必要澄清被工单选择延后的情况。

语义样本量仍不足以估计生产环境准确率。

Goal Coordinator 的真实复杂任务样本不足。

交互式 Web、联网 API、音频试听和主观质量验收尚未全面覆盖。

运行回执没有提供完整的实际账单金额。

因此下一步应重点验证系统的决策质量，而不是仅继续增加组件数量。

# 11. 已经发现的具体工程问题

## 11.1 执行时间线缺少 coordinate 阶段

本机核查发现：

`网页工作台/workbench.py`

执行时间线的阶段映射遗漏了 `coordinate`，可能触发：

`KeyError: 'coordinate'`

这属于明确的代码缺陷。

应修复并增加对所有合法阶段的覆盖测试。

## 11.2 外层调用的可观察性不一致

Intake Assessor 和 Acceptance Designer 主要记录在 SQLite 的 `outer_invocations` 中。

Goal Coordinator 的执行记录主要存在 Assignment / Run 回执中。

当前看板没有统一的外层智能决策查看器。

建议以后提供一个 Intelligence Timeline，能够按 Ticket 看到：

- 角色；
- 调用时间；
- 输入快照；
- 使用模型；
- 可见执行事件；
- 结构化提案；
- Engine 是否接受建议；
- 引用的证据；
- 失败与重试；
- Token 用量和耗时。

不要求展示模型未公开的内部推理过程。

## 11.3 Codex Session 的实际情况

三个外层角色目前使用 `--ephemeral`。

成功调用会产生临时 Thread，但不持久化成可在 Codex Desktop 中直接续聊的历史 Session。

目前适配器也没有保留对应 Thread ID 作为长期会话引用。

这并不说明系统错误。

我们倾向于继续让业务状态存在 Autoloop 中，通过统一的可观察性系统查看外层模型判断。

若未来确实需要持久化 Codex Session，应作为独立功能评估，而不是默认全部打开。

# 12. GitHub 开发体系的长期原则

本项目是基于上游开源项目二次开发的工程。

因此需要同时维护：

**Upstream：原始开源项目。**

**Our Repository：我们的改造版本。**

**Development History：我们的需求、架构、提交、测试和决策。**

推荐形成：

PRD Requirement → GitHub Issue → Code Commit → Pull Request → Test → Evidence → Release

但是 GitHub 不应该替代 Autoloop 的 SQLite 业务状态。

仓库中应保留：

- 正式 PRD；
- 架构说明；
- 技术接口与数据契约；
- ADR 架构决策；
- 实施计划；
- 测试矩阵；
- 脱敏证据；
- 变更和进度记录；
- 恢复操作说明。

不得上传：

- 真实用户私人消息；
- API Key；
- 认证文件；
- 本机私人配置；
- 运行中的原始数据库；
- 不适合进入仓库的原始日志和资产。

上游许可证、来源声明和版本差异需要持续保留。

现有 GitHub PR #4 尚属于受控候选，不能因为本机测试通过就视为正式发布。

# 13. 后续优化的优先方向

以下排序属于我们基于现有证据作出的设计建议，Codex 应在核对源码后给出进一步判断。

## P0：修复明确缺陷，完善执行可观察性

优先解决：

- `coordinate` 时间线异常；
- 三个外层角色记录不统一；
- 缺少可查看的 Intelligence Timeline；
- 真实故障原因和模型判断证据不够直观的问题。

这里不要求重建模型 Session。

## P1：提高 Intake Assessor 的实际判断质量

重点研究：

- 多张相似工单；
- 模糊需求；
- 原卡追问；
- 新目标与旧任务的关系；
- 关键澄清顺序；
- 不必要的用户交互。

通过正式评测数据判断是否需要更强模型或更丰富的只读检索工具。

## P1：扩大 Acceptance Designer 的适用范围

重点验证：

- Web 应用构建及真实交互；
- API 与外部服务；
- 音频软件；
- 桌面软件；
- 非固定格式交付物。

应优先改善验收能力目录与证据规则。

只有实际发现单次结构化调用信息不足时，再考虑将 Acceptance Designer 改为具有有限只读工具调用能力的 Agent。

## P1：测试真实复杂目标的长期自主执行

选择一个陌生、多阶段、存在真实失败可能的目标。

不预先替系统制定完整工作包。

验证从初始需求到最终交付，系统能否自主形成目标、设计验收、规划执行、处理失败并完成交付。

自动 DJ 软件可以作为其中一个真实测试任务，但不应成为整个架构唯一能处理的业务。

## P2：优化成本、模型选择和多 Agent 策略

比较：

- 低成本模型与高推理模型的路由质量；
- 单次模型调用与工具调用 Agent；
- 独立 Codex Run 与原生子 Agent；
- 固定阶段执行与动态重新规划；
- 直接使用 Codex 与通过 Autoloop 执行。

不要假设多 Agent 一定更快、更省钱或更可靠。

以相同目标和相同验收标准的真实对照结果为依据。

# 14. 必须避免的架构错误

## 错误一：为了更像 Agent 系统而创建更多 Agent

只有明确的新能力或真实瓶颈才能支持增加 Agent。

逻辑角色不等于必须拥有常驻进程和独立聊天历史。

## 错误二：让外层 Router 成为万能管理者

Intake、验收设计和跨阶段协调可以共享模型基础，但必须保持职责清楚。

Router 不应该管理所有技术实现细节。

## 错误三：让模型掌握正式授权

无论模型多强，权限、预算、状态及不可逆操作都必须受到程序控制。

## 错误四：让 Session 代替正式任务状态

Codex Session 可以结束、更换或不可恢复。

Ticket、Plan、Mandate 和 Evidence 必须持续存在。

## 错误五：将测试通过等同于真实价值实现

验证器必须与用户批准的完成标准一致。

“产生了文件”不等于“软件可以使用”。

“代码构建成功”不等于“整体产品达到目标”。

## 错误六：不断重写已经验证的基础设施

现有 Autoloop 的并行、恢复、SQLite、飞书和执行器已经积累真实验证结果。

任何重构必须有明确收益、影响分析与回归证据。

## 错误七：将长时间自动运行理解成无限执行

系统必须有授权边界、预算、有限重试、停滞检测以及必要的人工升级路径。

# 15. 后续 Codex 应怎样利用本文件？

此文档应成为长期架构依据，而不是一次性开发 Prompt。

之后当用户提出新的功能或优化要求时，Codex 应当：

**第一，核对真实代码。**

本文件记录的是设计共识和截至目前的已报告证据。新的源码、测试与运行事实可能更新技术判断。

**第二，判断需求属于 Outer 还是 Inner。**

不得将内层的普通技术实现问题错误地交给 Outer Router。

不得让内层未经批准修改外层的目标契约。

**第三，判断现有能力是否已经能够解决问题。**

优先复用。

**第四，明确为什么修改。**

每项重要修改需要记录：

- 当前问题；
- 实际证据；
- 用户价值；
- 可选方案；
- 技术代价；
- 风险；
- 推荐方案；
- 对现有能力的影响。

**第五，更新正式开发文档。**

涉及产品目标、系统行为、接口、状态或数据模型的修改，必须同步更新 PRD、架构、测试和开发记录。

**第六，用真实测试证明改进。**

不能仅凭模型说“已经优化”来认定改造成功。

# 16. 对当前项目下一阶段的正式建议

现在不建议立即重新设计新的大架构。

我们认为 Autoloop V2.0 的基本方向已经成立：

**Outer Loop：智能目标治理。**

**Inner Loop：Codex 复杂任务执行。**

**Autoloop Engine：权威状态与可靠调度。**

**Evaluation：根据可信证据判断完成。**

下一阶段更重要的是让系统做到：

1. 外层的每次智能判断可以被用户理解和复查。
2. 面对陌生复杂目标时，能够真正自主接单和设计验收。
3. 目标未完成时，能够根据可靠证据持续调整执行。
4. 在多轮执行和不同设备之间保持一致的目标与授权。
5. 不因增加智能组件而牺牲可靠性、成本和可维护性。

## 最终设计共识

**我们不是在设计一群不断聊天的 Agent。**

**我们是在设计一个以用户目标为中心、由智能决策与确定性机制共同驱动的长期自主工作系统。**

它应该具备三个最重要的特征：

**Autonomy（自主性）：** 尽量不依赖用户逐步指挥。

**Reliability（可靠性）：** 每一次执行、决定和恢复都受到可验证机制约束。

**Verifiability（可验证性）：** 最终交付必须有与目标一致的真实证据。

这三者同等重要。

不能为了更高自主性牺牲权限与可靠性，也不能为了更严格的工作流而让系统失去对陌生问题的智能适应能力。

**本文件应作为 Autoloop 未来持续优化的长期架构依据。**

除非真实测试或新的产品要求证明原有设计不合适，否则不应随意推翻已经确定的内外分层、唯一权威状态、版本化授权、独立验收与事件驱动智能等核心原则。
