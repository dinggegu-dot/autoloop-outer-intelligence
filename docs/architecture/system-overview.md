## 风险与回退

- 主工作区运行目录约 17 GiB，含私人工作成果；验收资料甚至包含 SQLite、WAL、消息与配置。使用独立 Git 对象库、逐文件白名单和变更审查。
- 三份活动数据库分别使用 SQLite Online Backup 读取已提交的 WAL 内容。工作台、收件库做 integrity_check，中台带应用自定义 card_hash 表达式索引，做 quick_check。副本逐个可读，三个进程之间没有全局原子时刻。恢复后按事件和 Run 对账。
- 恢复目录位于本机 Application Support 的 Autoloop Recovery 下，仅本人可访问。manifest.json 将三个归档、数据库逻辑路径及独立镜像与 SHA-256 关联。先在新的私有目录复核哈希并展开归档，把相应 sqlite3 镜像放回清单注明的位置，启动时重新创建 socket 和锁。采样从归档读取三端源码并与当时源码逐字节比对。完整恢复环境启动仍需单独演练。
- 原库提案、旧回执或执行报告不能单独决定新版通过。出现验收缺口须保留工单和产物供复核。
- 回退应用时先暂停新接单、核对活动 Run 并备份最新状态，再让旧版服务回到原配置。备份恢复在独立目录演练，避免覆盖升级后的用户操作。

## V2 实现

已鉴权的网页会话和本人私聊桥调用同一组工单命令。`outer_intake.py` 在 SQLite 事务中持久化来源、候选工单、澄清、版本、模型调用、授权和待投递通知。模型读取限长的当前快照；引擎使用来源、预期版本和动作白名单验证提案。接单、验收设计与目标协调各有输出契约，共用 `outer_model.py` 的受限调用适配器。

批准目标、验收和授权版本后，原工单通过已有 GoalRuntime 及 Hub/Worker 派工。明确替换要求会进入新版本；新授权使用独立工作区，保留原版证据。V1 控制入口拒绝直接更改 V2 状态。飞书原卡绑定已投递消息及版本，网页操作核对会话和 CSRF。跨端决定通过持久收件和通知记录恢复。

`outer_verification.py` 支持 CLI 输入输出、JSON 内容和静态 HTML。实时 API、浏览器交互及主观要求目前进入验证缺口。独立 Worker 针对冻结文件复验，记录执行器版本及产物摘要。协调器核对当前版本、宿主与验证环境、检查集合和证据摘要。目标交付从独立验收归档读取，下载时再次检查 SHA-256。模型的返工或重规划建议须引用当前失败证据，并受原授权和调用预算约束。

11 月 19 日晚补做了完整归档展开演练。在一个新建的本人私有临时目录分别展开工作区、中台、飞书三个归档，在各自的原相对路径放回一致性数据库镜像。只读核对获得工作台 10 个表、integrity_check=ok，中台 5 个表、quick_check=ok，飞书 16 个表、integrity_check=ok。原服务与测试消息监听仍在原位置。此次未从生产备份启动有外部副作用的机器人或重放历史事件。隔离 V2 的 Hub、Worker 和工单则在原试点路径实际重启恢复并完成复验。
