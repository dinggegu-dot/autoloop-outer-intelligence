当前团队工单按已确认的 Router 分工运行。后补的资料跟随订阅送到同一团队，方案、验收与交付归这张工单。下文保留历次架构决定及其实测范围。[当前设计](../product/router-ticket-teams.md)

**结论（2026-11-19）**　保留事件驱动的外层判断、程序控制的授权与状态转换、按派工运行的 Codex 执行器，以及绑定产物版本的独立验收。候选版已经用这套机制交付过两种本地 CLI 工具。把同样的结论推广到陌生的多阶段软件、交互式产品或主观质量，目前缺少真实端到端证据。

## 三、仍需真实实验验证的假设与建议

| --- | --- | --- |

| P1　陌生交付物能否获得足够的验收证据？ | 按浏览器交互、服务 API、桌面程序、音频听感、非固定格式分别准备合格与“表面成功”的对照交付物；预先约定实际操作、预期和人工评价人。记录误放行、误拒、无法判定及复验一致性。 | 能稳定区分好坏结果才登记相应验证器；主观部分先验证绑定产物摘要的人工签收、过期拒绝与重验，再考虑自动结案。 |
| P1　多阶段陌生目标能否在一次授权后自主交付？ | 待有适合的真实工单时，提供用户目标和资源边界，保留独立评价标准。记录每次人工介入的原因、授权是否变化、首次失败到修复的路径、全目标终验与可用性。 | 若各阶段通过但用户目标失败，先补契约或证据；若证据充足而选错行动，再调协调器。先量化局部失败由外层处理的开销，再决定是否改变分流。 |
| P2　更强模型、工具型角色、原生子 Agent 或动态重规划是否划算？ | 固定目标、起始快照、权限、包容失败的预算与验收人。配对比较直接 Codex 与 Autoloop；在 Autoloop 内再分别对照模型强度、结构化调用与受限工具、独立 Run 与原生子 Agent、固定计划与重规划。每次只改一项，记录重复试验的交付率、返工、人工轮数、耗时及含缓存的用量。 | 同等质量下降低人工或成本，或同等预算提高交付率，才考虑扩大使用。账单金额需独立账单来源，缺失时只报告 tokens 与时间。 |
| 发布前　恢复与部署能否承受真实故障？ | 在隔离、可回滚的环境注入回执丢失、重启和版本变化，核对同一授权、归档摘要、重复副作用和未决事项。按操作手册记录适用版本、恢复时间与不能自动判定的情况。 | 有恢复和回退证据后由维护者单独决定发布。私有分支推送、本机回归和早期云端作业分别记账。[运行与回滚手册](../operations/pilot.md) |
